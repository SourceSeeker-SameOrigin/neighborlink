# QA228 商家预约同人换小区保护（2026-11-28）

| 5W2H | 结果 |
| --- | --- |
| What | P60 商家预约已加载后，同一住户更换小区时使旧提交与原订单入口失效。 |
| Why | 实际页面接合成身份：A 小区需求仍显示在 B 小区，旧按钮可发出一次 `createBooking`。服务端另行校验，本轮没有证明云端接受，也没有真实订单。 |
| Who | Codex 按用户已统一选择的推荐方案修复和回归；真实多小区体验成员验收待安排。 |
| When | 先阻断旧按钮和迟到结果，再复跑已有换人及找单边界；云端与真机另验。 |
| Where | `miniprogram/shops/booking/booking.js`，只改前端。 |
| How | 加载和操作同时核对本人及小区；变化时清除旧需求、地址和页面内原单引用，重新只读加载。创建结果迟到时不提示、不付款、不导航。新凭据按本人、小区、服务隔离；旧格式先找原单，查无时明确提示并可主动开始当前小区新预约。已明确选择新预约后，当前小区跳过同一旧编号，旧凭据仍保留。 |
| How much | 前端 1 页及恢复提示、专项回归；云端新增订单、付款和资源均为 0。 |

手工复验：在同一账号拥有两个小区的隔离工程或开发会话中进入 P60，填写 A 小区需求但不提交；切 B 小区后触发旧按钮，应不发创建请求、不打开 A 的原单，页面只读重载 B，旧需求清空。A 小区提交结果未知后进入 B，小区 B 应使用独立凭据；旧版凭据应先找原单，未找到时显示原小区未知提示和主动开始新预约入口。正常同区提交仍只建一笔；创建请求已发出后切小区，迟到结果不得付款或跳转。真实多小区及旧凭据迁移仍待验，不能据此把 P60 整页判为通过。
